# Pharlux benchmarks

**Last updated: 2026-07-06** · Applies to: Pharlux v1.2.0

On a single **4 vCPU / 8 GB VPS** (disk fsync ~1.3 ms), Pharlux v1.2.0 sustains **350,000 durable OpenTelemetry metric points per second** at a production batch size of 1000, with **zero errors** and ~7 ms average request latency. These are first-party numbers, measured with a load generator that ships in the Pharlux source tree, and they are reproducible with the steps below.

We state the exact hardware for every figure, because it matters: sustained durable ingest is **single-core-bound** (see [below](#read-this-first-throughput-is-single-core-bound)), so the number you get scales with your VPS's CPU and disk.

## Read this first: throughput is single-core-bound

Every point Pharlux accepts is made durable through its write-ahead log, and the WAL's fsync path runs on **one core**. Sustained durable ingest is therefore gated by **single-core CPU speed and disk fsync latency**, not by adding vCPUs:

- A faster CPU or an NVMe disk pushes the number **higher**.
- A slower or heavily-shared commodity VPS pushes it **lower** — on budget shared hosts we have measured the same build sustaining closer to 60,000–90,000 points/sec on the same nominal "4 vCPU" tier, purely because the underlying cores are slower.

We verified this spread directly: across **three independent 4 vCPU / 8 GB hosts of the same class**, all three cleanly sustained **350,000 points/sec at zero errors** for 30 s; one faster host reached ~450,000. We headline **350,000** precisely because every host we tested cleared it — it is the reproducible figure, not the best one.

So read these figures as *"what a healthy 4 vCPU / 8 GB VPS does,"* not a fixed guarantee. For honest context: a team running **1–10 services** rarely generates more than a few **thousand** points per second. Even the low end here is orders of magnitude beyond a typical small-team workload — the point is not a throughput crown, it's that **Pharlux won't be your bottleneck on cheap hardware.**

## Headline results (4 vCPU / 8 GB VPS, fsync ~1.3 ms)

| Metric | Result | Notes |
|---|---|---|
| Sustained ingest (batch size 1000) | **350,000 points/sec** | zero errors, sustained 30 s |
| Average request latency | **~7 ms** | OTLP HTTP/protobuf, end to end |
| Errors at the sustained rate | **0** | throughput within 5% of requested |
| Static binary size | **86 MiB** | statically-linked musl, OpenSSL-free |

## What WAL group commit (v1.2.0) changed

v1.2.0 amortizes the WAL `fsync` across a whole group of queued records instead of one `fsync` per batch ([ADR-0023](/docs/)). The benefit is **largest at small batch sizes**, where per-batch fsync dominates. The A/B below isolates that change on an **earlier reference box with a slower disk (fsync ~1.9 ms)**, running both builds back to back on the same box; the headline above was re-measured on current, faster hardware, which is why its batch-1000 figure is higher. Same load generator, per-batch-fsync build (v1.1.x) vs group commit (v1.2.0), driving 400,000 points/sec:

| Batch size | v1.1.x (fsync per batch) | v1.2.0 (group commit) | Gain |
|---|---|---|---|
| 50 | ~23,000 points/sec | **~361,000 points/sec** | ~15× |
| 200 | ~89,000 points/sec | **~394,000 points/sec** | ~4× |
| 1000 | ~200,000 points/sec | **~250,000 points/sec** | ~1.25× |

At a batch size of 1000 the per-batch fsync cost is already spread across 1000 points, so both builds are strong and the gain narrows — group commit matters most for exporters that flush small batches often. **The on-disk WAL format is unchanged** (ADR-0018); a group is simply N framed records made durable together.

## The load generator

The benchmark uses **`pharlux-loadtest`**, a small harness that ships in the Pharlux source tree (`pharlux-loadtest/`, AGPL-3.0). It sends OTLP metric points over HTTP/protobuf at a configurable rate and reports throughput, average latency, and error count.

Each request carries a batch of points spread across eight realistic gauge metrics — `http.request.duration`, `http.request.count`, `cpu.usage`, `memory.used`, `disk.io.read`, `network.bytes.sent`, `gc.pause.duration`, and `thread.count` — each tagged with `host` and `service` attributes, so the payload shape matches a real OpenTelemetry Collector export rather than a single trivial counter.

| Flag | Default | Meaning |
|---|---|---|
| `--target` | `http://127.0.0.1:4318` | OTLP HTTP endpoint |
| `--rate` | `30000` | target points per second |
| `--duration` | `30` | test duration (seconds) |
| `--batch-size` | `1000` | points per OTLP request |
| `--workers` | `16` | concurrent sender tasks |

## Reproduce it

```bash
# 1. Install Pharlux v1.2.0 on a 4 vCPU / 8 GB Linux VPS (see the getting-started guide)
curl -L https://github.com/Veltara-Works/pharlux/releases/download/v1.2.0/pharlux-v1.2.0-x86_64-unknown-linux-musl \
  -o /usr/local/bin/pharlux && chmod +x /usr/local/bin/pharlux
sudo pharlux install && sudo systemctl enable --now pharlux

# 2. Build and run the load generator from the source tree
git clone https://github.com/Veltara-Works/pharlux && cd pharlux
cargo run --release -p pharlux-loadtest -- \
  --target http://127.0.0.1:4318 \
  --rate 350000 --duration 30 --workers 16 --batch-size 1000
```

The harness prints a running points/sec figure every five seconds and a final report:

```text
Load Test Results
=================
Duration:      30.0s
Points sent:   10500000
Requests:      10500
Errors:        0 (0.00%)
Throughput:    350000 pts/sec
Avg latency:   7.69 ms

PASSED: 350000 pts/sec (within 5% of --rate)
```

It reports **PASSED** when sustained throughput is within 5% of the requested rate. Drive `--rate` past your host's ceiling and the reported throughput plateaus while latency and errors climb — that plateau is your box's single-core WAL ceiling. Check your disk with `dd if=/dev/zero of=/tmp/t bs=4k count=500 oflag=dsync`: a slower fsync means a lower ceiling.

## What this does and doesn't tell you

- **It measures sustained *durable* metric ingest** — the hot path from OTLP request through WAL fsync — on commodity hardware, not an in-memory or synthetic micro-benchmark.
- **It is single-node and single-core-bound.** Throughput tracks single-core CPU and disk fsync; it does not scale by adding vCPUs. Multi-VPS clustering is future work.
- **Query latency, memory footprint under load, and disk-growth projections** are tracked separately and will be published here as additional first-party benchmarks.

## Frequently asked questions

### How fast is Pharlux ingest on a single VPS?

On a 4 vCPU / 8 GB VPS with ~1.3 ms disk fsync, Pharlux v1.2.0 sustains **350,000 durable points/sec** at a production batch size of 1000, with zero errors. Because sustained durable ingest is single-core-bound (gated by the WAL fsync path), throughput scales with the host CPU and disk — faster hardware goes higher, a slower or heavily-shared VPS goes lower. We state the exact hardware for every number.

### Can I reproduce the Pharlux benchmark myself?

Yes. The load generator (`pharlux-loadtest`) ships in the Pharlux source tree under AGPL-3.0. Install Pharlux, then run `pharlux-loadtest` against its OTLP HTTP endpoint with the flags above. The harness prints points/sec, average latency, and error count, and reports PASS when sustained throughput is within 5% of the requested rate.

### What did WAL group commit (v1.2.0) change?

v1.2.0 amortizes the WAL `fsync` across a whole group of queued records instead of one per batch (ADR-0023). On slow-fsync disks the effect is dramatic at small batch sizes — at a batch size of 50, sustained ingest rose from ~23,000 to ~361,000 points/sec — and narrows at large batches where the per-batch fsync cost is already amortized. The on-disk WAL format is unchanged.
